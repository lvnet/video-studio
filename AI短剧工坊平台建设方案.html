00 / VISION & SUMMARY愿景与结论先行

前期以自用为主线：先把「剧本 → 提示词 → 资产 → 视频 → 成片」这条链路在自己手里跑通、跑稳，再把工具以开源方式发布出去。官网、支付、账号、租户体系等获客与商业化组件全部后置；它们不产生创作价值，只会拖慢前 3 个月。

项目愿景：人人都能搞创作，不受硬件、算力限制。
落到产品上有三条硬要求：① 算力可插拔——同一套流程既能跑在本地显卡，也能跑在云 GPU 或云端 API；② 设备无门槛——没有显卡的普通电脑也能完成创作；③ 成本可预期——提交前给出估算，设置预算上限，不让「门槛」从硬件变成账单。

01 / BENCHMARK对标产品拆解

参考 kfchenzhan.com.cn「ComfyUI 短剧工坊」的工程实现与八步流程，但不复制它的商业路径。它把本地脚本工具包装成有版本、有价格的产品；我们把自用工具打磨成开源公共品。

它到底是什么

产品形态

  • 官网：项目演示视频、8 步流程、v4 更新点、版本价格、扫码支付、GitHub 入口
  • 控制台：Python 标准库 + 单文件原生前端，本机跑在 127.0.0.1:8890
  • 生成端：远程 ComfyUI 跑 H3 工作流，LLM / 生图 / 视觉质检均支持本地↔云端切换
  • 数据：console.db（SQLite）+ 素材目录 + config.json

八步制作链

  1. 创建项目（画幅 / 风格 / 集数）
  2. 剧本：梗概生成或导入原稿
  3. 拆镜：按场景 / 动作 / 对白拆成镜头表
  4. 参考资产：角色四视图、场景图与音色锚点，人工批准
  5. 提示词：扩写为 H3 三段式规范，R2V 自动六段式包装
  6. 提交生成：T2V / I2V / R2V，批量与成本闸门
  7. 监控挑片：实时进度、候选比对、失败码诊断
  8. 精修成片：升清、裁头杂音、字幕/CTA、导出 MP4

它的商业设计（作为参考，不照搬）

版本价格定位对我们的启示
v1 / v2免费开源（MIT）跑通制作链 / 固定八步基线开源是建立信任与传播的最低成本方式，值得直接采用
v3 导演台版¥500镜头与版本管理、数据库规则、提示词版本链「版本管理」是真需求，应放进开源核心功能
v4 完整制作版¥2,000多集、原稿续写、超分、多服务器接单、Win/Linux 部署多机与超分是进阶能力，开源版可按插件方式逐步放出
云 GPU约 ¥2/小时（参考价）低配电脑也能用与我们的愿景一致，但我们做「用户自带算力/API」，不靠转售算力赚钱

可借鉴的是它「先讲清楚边界」的写法：软件价格不含 GPU、存储与模型 API 费用，授权范围购买前确认。我们开源版同样要在 README 里讲清楚：软件按现状提供，模型权重与 API 费用由使用者自行承担。

它暴露出的短板，就是我们的设计起点

① 单人本地工具味重

SQLite + 单文件前端 + 守护进程，缺少可演进的数据模型与接口边界。我们用 PostgreSQL + 明确 API 分层重写核心。

② 算力切换不彻底

本地 / 云端切换散落在配置里。我们把它收敛成统一的「算力适配层」，这是实现愿景的关键抽象。

③ 交付靠人工

安装部署需要用户自己配环境。我们用 Docker Compose 与一键环境检查降低门槛，而不是卖安装包。

02 / POSITIONING产品定位与开源原则

一句话定位

开源、自托管的 AI 短剧创作工作台：以项目为中心管理剧本、角色资产、分镜与版本，把 H3 视频生成、超分、合成编排成可追踪、可复现的流程；通过统一的算力适配层，让没有显卡的人用云端 API、有显卡的人用本地 GPU、有多台机器的人用云 GPU 集群，跑的是同一套工作流。

愿景拆解：三条产品硬要求

不受硬件限制

无显卡设备只跑浏览器与控制面，生成任务交给云端 API 或云 GPU。首次使用不需要下载 40GB 模型。

不受算力限制

算力是「可插拔后端」，不是产品的一部分。用户随时切换、叠加自己的机器，不被单一供应商绑定。

人人都能创作

把 H3 提示词规范、角色一致性、失败诊断封装成向导和规则，用户写故事，不写参数。

前期使用者与开源受众

对象痛点我们提供的价值阶段
自己 / 核心小团队多集制作中素材、提示词、版本混乱；抽卡成本高自用提效：流程可追溯、可重跑、成本可见第一优先级
开源创作者 / 独立开发者想要可改造的流水线基线，不想从零写MIT / Apache-2.0 代码 + 示例剧本 + 一键检查脚本首个开源版本

价值回流与长期选项（前期不以变现为目标）

1）自用提效（首要价值）

减少重复找文件、重复写提示词、重复试错的时间；按项目沉淀角色资产与提示词版本，让下一集比上一集更快。

2）开源影响力

GitHub Star、外部 Issue 与 PR、公开案例与硬件运行报告。这些是后续一切可能性的前提，也是验证「人人可用」的真实反馈。

3）社区赞助与支持（后期可选）

GitHub Sponsors / 爱发电等自愿赞助；有偿技术支持与定制开发。只有在项目被真实使用后才有意义。

4）托管实例 / 企业定制（远期可选）

若社区规模与合规条件成熟，再考虑提供开箱即用的托管服务。它不进入前两期规划，也不影响开源版本的功能完整性。

自用成本测算（不是定价）：一集 60 秒成片约 6–10 个镜头，按平均 3 次抽卡 = 200–300 秒输出；全用 768P API 约 ¥100–150/集，全 2K 约 ¥160–240/集，加 LLM/生图/超分后的自用预算建议按 ¥200–400/集 准备。有本地显卡时用机时与电费替换这部分支出，但要计入排队与失败率。

03 / ARCHITECTURE总体架构

三层解耦：创作层负责体验，控制面负责项目数据与任务编排，算力适配层负责把同一个任务翻译成 API 调用或 ComfyUI 工作流。官网与社区只在图中以虚线标出——它们是后期可选模块，不进入首版开发。

三种算力执行模式（同一工作台，按设备选择）

A. 纯 API 模式（先做）

本机只跑工作台与控制面，生成全走 MiniMax H3 / LLM / 生图 API。目标：普通电脑也能创作。无需下载模型、无需显卡，按量付费且预算可控。

B. 本地 GPU 模式（随后）

Docker Compose 一键起控制面 + ComfyUI，本机显卡跑推理，数据不出内网。目标：有卡用户的私密与批量生产。模型走国内镜像预热。

C. 云 GPU / 多机分体（后期）

GPU 机器装轻量 Agent，主动注册能力标签并按任务类型接单；轻电脑只跑网页。目标：低配设备与多机工作室。

统一原则：三种模式共用同一套任务接口和数据模型，区别只在执行后端。先做 A 验证愿景，再补 B 覆盖有卡用户，C 放到开源增强阶段。不要为某一种模式单独 fork 代码。

06 / WORKFLOW端到端制作流程

这是使用者真正感知到的产品，也是所有技术选型的出发点。每一步都要有「可编辑、可重跑、可追溯」三个属性；无显卡用户走 API 后端的步骤完全一致，这正是愿景的体验验证。

  1. 创建项目：填片名、选择 9:16 或 16:9、风格（3D 写实/漫剧）、集数、目标单集时长 → 生成项目骨架。
  2. 剧本：粘贴梗概让 LLM 生成分集大纲，或导入已有原稿；AI 改写后人工确认，保存版本。
  3. 拆镜：按「场景 / 人物动作 / 对白 / 时长」拆成镜头表，每个镜头生成结构化字段，缺字段高亮。
  4. 参考资产：为每个角色生成四视图、场景图与音色锚点；人工批准为硬门槛，并锁定 asset_version。
  5. 提示词：规则引擎按权威 Schema 扩写为 H3 三段式；对白按 (S1)/(S2)↔voice_id 绑定；R2V 自动六段式完整包装并指定主参考。
  6. 提交生成：执行累计成本闸门（预估 + 已花 + 在途 ≤ 上限）并确认；按镜头批量建任务，选择 T2V/I2V/R2V。
  7. 监控与挑片：WebSocket 实时进度；每段生成 2–4 个候选，人工选中或让质检模型初筛；失败按最小错误码一键重试。
  8. 精修成片：后端无关的「升清」——API 模式走 768P→2K 重生，本地模式用 SeedVR2（2× 两次）；裁头杂音、拼字幕与片尾 CTA，导出 MP4。
卡点与闸门分开：第 2、4、5 步是「人工质量确认」，唯一强制的成本闸门在提交步：做 (预估 + 已花 + 在途冻结 ≤ 上限) 原子校验，提交时冻结、成功转实际、失败释放。AI 短剧最大的成本是抽卡，一次错误提示词批量生成 20 段，成本直接翻几倍。

08 / DEPLOYMENT部署与算力方案

A. 纯 API 模式（默认，先做）

  1. 本机跑 React 工作台 + FastAPI 控制面（Docker Compose 或本地进程）
  2. 算力全部走 MiniMax H3 / LLM / 生图云端 API，零模型下载、零显卡依赖
  3. 配置里填自己的 API Key，成本自己可见、上限自己设
  4. 这是「无显卡也能创作」的验收场景

优点：门槛最低、2–4 周可用；缺点：按量付费，需要成本闸门。

B. 本地 GPU 模式（开源版主场景）

  1. Compose 同时起工作台、控制面与 ComfyUI
  2. scripts/check_env.py 式一键环境自检，逐项给修复建议
  3. 模型从国内镜像下载，支持离线导入模型包
  4. 本机 GPU 跑视频/超分，云端 LLM 兜底文本与生图

优点：数据不出内网、批量成本更低；缺点：需要显卡与磁盘空间。

C. 云 GPU / 多机分体（后期）

  1. 控制面跑在轻量主机或本机
  2. GPU 机器装 Agent，WireGuard / Tailscale 组网，主动注册
  3. 能力标签分流：图像 / 视频 / 超分各自独立接单
  4. 模型预置 + 磁盘缓存 + 节点健康检查

优点：低配设备与多机都能用；缺点：运维复杂度最高，放 P1/P2。

统一原则：三种模式共用同一套任务接口和数据模型，区别只在「算力后端配置」。默认交付轻量 all-in-one profile（本地目录 + 内存队列，标注迁移到 PG 的路径），标准 profile 用 PG+Redis+MinIO；Windows 本地 GPU 要明确 WSL2 或原生 ComfyUI 的支持范围。不要为某一种模式单独维护分支。

09 / SCHEDULING & COST调度与成本可见

调度器既要服务多机场景，也要服务单人单机。核心不是「把机器塞满」，而是让任何设备都能以可预期的方式完成创作——这是愿景在工程上的第二层落点。

调度器设计要点

能力匹配

节点上报 capabilities_json，例如 {"model":"h3","mode":["r2v","i2v"],"vram":24,"upscale":"seedvr2"}。调度器按任务需求筛选候选节点，避免把 R2V 派给没加载 Ref2VA 权重的机器（否则会悄悄回退 FL2VA，身份锁定变弱）。

租约与幂等

派单写 30 秒租约并续期；心跳丢失则任务回队列。提交侧用 idempotency_key 去重，网络重试不会重复生成、重复扣费。

失败与重试

错误分「可重试」（超时、节点离线、OOM）与「不可重试」（提示词违规、参数非法）。指数退避重试 3 次后进死信队列，人工可见。API 后端要把供应商错误码翻译成中文诊断。

成本归集

每个任务记录 cost_estimate_cents / cost_reserved_cents / cost_actual_cents：提交时冻结预留、成功转实际、失败释放。API 按输出秒数 × 单价，GPU 按占用机时；按项目、集、镜头出报表。

算力适配器接口（伪代码）

class Backend: capabilities(); health(); estimate(task) -> Cost; submit(task) -> task_id; poll(task_id) -> Progress; fetch(task_id) -> Artifact(storage_uri, sha256); cancel(task_id); normalize_error(provider_error) -> FailureCode

Artifact 必须含规范化 storage_uri 与 sha256：API 模式上传为 no-op，本地/云 GPU 由 Worker/Agent 主动推送对象存储（控制面无法拉取 NAT 后的文件）。上层业务只认 Backend，切换后端不改变剧本、提示词和项目数据。
